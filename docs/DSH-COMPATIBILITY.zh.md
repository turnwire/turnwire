# DSH 兼容性

## 策略

兼容性不再要求 DSH 版本等于固定基准。核心认证 RPC 必须提供符合约定的请求关联、会话身份和运行状态；新增字段允许出现。可选模型目录不可用不会被误判为整个核心接口不兼容。上游未提供的版本或能力信息明确保持未知，不伪造协议握手。

首次安装解析 registry `latest` 为精确版本。显式 `turnwire start --update-dsh` 在新版本目录安装，并在隔离 HOME 中检查实际认证接口，通过后才原子切换私有配置 `managed-dsh.json`。旧安装保留；失败不切换，不自动降级，不热更新活跃会话，不修改外部 DSH 或自定义入口。普通启动不会自动持续升级。选择文件仅由 npm 启动器使用，不更改旧版系统服务安装器。

## 持续测试

`.github/workflows/dsh-compatibility.yml` 每天 04:23 UTC、相关 PR/main 推送、手动操作及发布校验时，在 Linux/macOS 分别测试：

- 基准 `0.1.5-rc.2`。
- npm `latest`。
- npm `next`。

每个标签先解析为精确版本，禁用 npm 生命周期脚本，隔离 HOME、XDG 和 npm cache。只使用非秘密的假密钥，不发起模型推理请求。测试包括实际托管及外部 DSH 启动、认证快照、真实模型目录、空会话创建、重启恢复及进程所有权。停止 Turnwire 必须关闭自己的进程，而保留外部 DSH；测试结束再显式清理测试自己的外部实例。

独立报告工作流只读取本仓库 main 的定时或手动运行元数据，不检出代码、不下载产物。失败更新机器人 issue，完整矩阵成功才关闭；PR 和复用发布检查没有 issue 写权限。

## 边界

CI 配置不等于已经通过，以具体执行结果为准。`latest` 可能低于 `next`；标签由 npm 发布者维护。认证只读探针不等于完整推理兼容。

未覆盖真实模型流、工具执行、审批、推理中的 steer/取消、图片推理、可选上下文信息、真实密钥有效性、所有 CPU 架构和所有更新竞争条件。网络或 registry 错误同样会导致检查失败，需要调查后才能归因上游不兼容。没有上游稳定协议承诺，就不能保证“永远最新、永远兼容”。
