# Capability parity and code ownership

The Web/PWA composer sends with Enter and inserts a newline with Shift+Enter; Alt+Enter retains steering. IME candidate confirmation and held-key repeats never send. Existing session permission and busy-state checks still apply.

## Platform-specific installation details

Choose clients independently from the execution host. The current native desktop implementation targets macOS 14+ and requires Xcode 16+ / Swift 6 to build: from the separate desktop checkout, `cd ../turnwire-desktop && bash scripts/bundle.sh && open dist/Turnwire.app`. The bundle is ad-hoc signed; public native distribution additionally requires Developer ID signing and notarization. These are requirements of that optional client, not an assumption about every user's host.

The current background host installer targets Linux with systemd: run `scripts/install-linux-host.sh` from a built release after creating the private DSH environment file (default `~/.config/turnwire/dsh.env.json`; supported overrides include `TURNWIRE_CONFIG_HOME`, `XDG_CONFIG_HOME`, and `TURNWIRE_DSH_ENV_FILE`). See [quickstart](QUICKSTART.md) for this specific installation path. npm host platform restrictions and tested environments remain documented in [npm distribution](NPM.md); neutral product wording does not extend those compatibility claims.

Web Settings never echo saved pairing codes or local tokens into editable fields. Replacing a connection requires fresh credentials; canceling preserves the current connection. “Remember connection in this browser” controls browser persistence only, not host authorization: switching it moves the current credential between localStorage and sessionStorage immediately. Enabling notifications does not implicitly enable credential persistence. CLI/native credential storage mechanisms and all connection permissions are unchanged.

Local CLI/TUI and native host management share authenticated `/maintenance` status/begin/cancel/compact operations. A durable owner-token lease blocks new Turnwire task mutations while allowing cancellation and resolving pending approvals/questions. The daemon applies the same admission counter to local management writes and their full asynchronous deployment, remote-configuration, direct-listener and notification lifetimes. Readiness requires these host operations and managed runtime roots/descendants/queues to be known idle; unknown fails closed. Restart recovery cancels approvals belonging to the previous runtime connection before checking the lease, without resuming runtime work. This does not gate independent DSH clients or unrelated runtime sessions. A ready lease survives daemon restart until explicitly released. After release, explicitly reapplying the saved remote configuration reconciles desired configuration with actual transport state, including startup suppressed by the lease. Identical requests must not restart a transport that is already connecting, retrying or serving; readiness labels are observations, not lifecycle ownership. `maintenance compact` removes only rebuildable export cache, checkpoints and vacuums SQLite; journal sequences and all command receipts are retained indefinitely to preserve replay/idempotency. Daemon authentication retains its existing `--token` flag; the distinct maintenance owner flag is `--lease-token`.

Core shutdown ownership is distinct from maintenance authorization: sealing rejects new RPC and transport work, while admitted reads, mutations and automatic approval tasks are tracked through completion. Host teardown may finish before final drain; runtime subscriptions and storage are released only after owned tasks settle. Deployment subprocesses remain owned until actual close, including timeout/abort escalation; terminating SSH alone does not prove the remote installer stopped. Relay push background failures are observed and reported, and do not bypass database cleanup.

Session creation atomically journals its public identity and durable creation intent before allocating a runtime root. A failed allocation/model step returns a visible error-state session with the same resumable identity, not an orphan hidden behind a generic failed request. `session.resume` continues incomplete creation. An established DSH root that is missing, or whose replay cursor regressed, fails closed instead of silently recreating a fresh root under old history/cursors. Question answering has one terminal owner; queue preconditions are checked inside the session lock. Status reconciliation cannot overwrite a newer runtime event, and unknown/late approval resolution cannot resurrect an ended turn.

Invitation consumption is an atomic comparison against the current persisted credential, with current authorization rechecked after asynchronous crypto. Concurrent Relay/Direct consumers cannot install different keys from the same invitation; same-key acknowledgement recovery remains idempotent.

Required `RemoteStatus.health` exposes `relayRegistration`, `tunnelProcess`, `publicReachability`, and `deviceConfirmed` as `unknown|ready|off|error`. CLI/TUI and native local management render the same fields. Public reachability remains unknown without independent evidence; no unsolicited external probe runs. Paired PWA clients are not granted these host-administration operations.

Product TypeScript callsites use the SDK's method-derived `call(method, params)` API; there are no `rpc` or `callTyped` methods. Shared encryption, endpoint validation and retry primitives now live in the independent `@turnwire/wire` package, not a server dependency on the client SDK barrel. Record export reads persisted fragments through an isolated worker with its own read-only SQLite connection and a private revision-pinned cache. Export admission, execution time and record size are bounded; the daemon does not concatenate the entire record on its event loop. Shutdown and storage maintenance cancel exports and release their readers. Worker startup failure rolls back request admission and temporary resources; cleanup retains ownership until release succeeds. Cleanup failure is reported to maintenance/close and can be retried, rather than becoming an unhandled background rejection or a permanently poisoned cleanup chain. While a maintenance lease is held, new `history.record` exports are refused; ordinary history previews remain readable. These limits cover export, not every ingestion or preview allocation.

The approval inbox is labeled **Approvals** in the PWA and native app (**审批中心** in Chinese); CLI/TUI help uses the same terminology. The existing `inbox` command, `inbox.page` RPC, notification routing and persisted records are unchanged.

Local installations use [XDG directories](XDG.md), without detecting or migrating a legacy layout. Daemon and CLI share one Node-only resolver; native local connection discovery honors explicit client/config overrides and the XDG config default. `TURNWIRE_STATE_HOME` replaces the removed `TURNWIRE_HOME`; config, data and cache remain separate under `TURNWIRE_CONFIG_HOME`, `TURNWIRE_DATA_HOME` and `TURNWIRE_CACHE_HOME` or their respective XDG defaults. Saved native Keychain/UserDefaults connections and remote wire contracts are unchanged. Native discovery changes require macOS compilation/testing (not available in the Linux validation environment).

Per-session auto-approval choices are stored by Core, not in client-local preferences. The shared command and authoritative snapshot preserve an explicit choice across reconnects and host restarts; this does not depend on keeping any client open. New sessions default off; disabling or archiving clears it, and old event journals do not restore prior transient authorization.

[Image messages](IMAGES.md): PWA supports image selection/paste, prepared previews/removal and explicit sending; CLI/TUI use `send <session> [text] --image <path...>` through the SDK. Native code includes a local image picker and reference reads, but macOS compilation/live UI verification remains pending. Runtime `imageInput` advertises transport only: the selected model may reject images. History and text exports retain reference metadata, not embedded bytes. Images do not grant host-administration access.

The PWA footer child list is limited to verified launches in the latest started human turn and their descendants. Queued and steer messages do not start another turn. A new human turn clears the old list; historical readers remain at their original transcript positions. If bounded history omits the turn boundary or launch receipt, the UI does not guess ownership; loading older records can restore it. DSH inactive includes persisted children whose execution activation has already been released, not necessarily live OS processes. Do not kill processes or delete history based on that flag.

The [mobile presentation audit](MOBILE-AUDIT.md) records narrow-toolbar, short-viewport and touch-target fixes, browser coverage, and physical-device/focus/scroll limitations. Mobile approval mode remains in the existing composer toolbar; Stop is compact, model labels shrink before pinned actions, and long workspace paths preserve their leaf end.

CLI, the interactive terminal (`turnwire tui`) and the native desktop are clients of the same Turnwire host. With the same connection permissions, they must support the same product operations and observe the same state. UI mechanics may differ: a workspace path vs NSOpenPanel, a terminal QR vs NSImage, or a printed link vs a clipboard button.

## Context occupancy and steering

Session `context` is optional runtime-owned data carried by snapshots and `session.updated`: `contextWindow`, last-request `pressureTokens`, and estimated next-request `projectedTokens` are independently optional. Clients must not infer capacity from a model name, confuse cumulative token use with context occupancy, or treat missing values as zero. Prefer the projected value and label it estimated; show a percentage only with a known positive window. Web, CLI/TUI and native session presentation use the same fields. Native source/tests require macOS execution before claiming native UI validation.

Steering means delivery at the current turn's next execution-step boundary, not aborting an active model response/tool or moving to the front of a future-turn queue. Web distinguishes ordinary `next-turn` waiting from `next-step` steering pending consumption, preserves runtime queue targets and does not offer repeated steering on already-steered items. Long-running steps can delay consumption; accepted steering is not proof the model has already acted on it. The pending-queue edit/remove/steer controls currently remain Web-only; CLI/TUI and native support sending steering messages, but pending-queue controls are an existing capability-parity gap, not claimed as covered by this change.

Host administration uses authenticated local `/remote` and `/devices`. A paired phone or remote CLI can operate sessions and approvals, but cannot change host settings or pair additional devices. This is a connection-permission boundary enforced by the daemon, not a missing UI feature. PWA currently serves this paired-phone role.

The child view (`subagent.list`, `subagent.history`) shows real execution messages and tool input/results, not just the optional plan. It is available in the PWA and CLI/TUI; native implementation is included but requires macOS compilation and live verification. Queue controls, delegated approvals (`session.autoApprove`) and answering questions (`question.answer`) retain the desktop gaps shown above. A delegated session is also the one place where no person reads an approval before it is granted — and a question is never delegated, because it has no safe default. A question is rendered where the agent asked it, as part of the conversation rather than as a control somewhere else on the page: choices and typed answers are drafts until the card's single submit button is pressed. Every question in a batch must have an answer before submission; a row cannot silently finalize unanswered siblings. Enter follows the same rule and does not submit during IME composition. Pending controls remain mounted but disabled during requests or disconnection. The answered card remains in the transcript, which is also what the exported transcript and `turnwire history` print. This is PWA presentation validation; the shared question-answer wire contract and CLI's explicit answer command are unchanged. Completed turns retain all assistant messages in chronological order: the last message is not assumed to summarize earlier content. Tool details can still be opened individually; a returned delegation tool call does not prove its background child has completed. A question's options are a column, not a row of centred labels: every option starts at the same left edge, keeps the same width, and carries its description underneath, because ragged labels are what made an option list read as broken. Nothing in the card may widen it either. An answer someone typed is shown in full where it was given, and a value with no break opportunity in it — a path, a key, a digest — wraps inside the card instead of running past its edge, since a card that can be panned sideways is the same defect as a queued prompt that can. The same holds for the agent strip: a row is the control that opens the child, and the plan it reveals is a three-column list — mark, state, and the step itself — whose columns line up down every row. The strip prioritizes running children and retains nonrunning children for reading their own history; opening a row shows the runtime's own description of that child (whether it can be continued, and where it sits) plus the plan it reports, and a child that reports no plan says so rather than showing an empty table. `turnwire agents` prints the same thing for every child at once, so the terminal does not need a second command to see a plan.

The PWA keeps two child entry points: the running strip above the composer, and a persistent inline reader at the actual delegation tool's transcript position. Launch calls are not swallowed into a collapsed group of unrelated tools. Successful continuable background receipts are joined by exact durable ID to the root's direct-child catalog; duplicate labels and out-of-order completion do not change placement. Inactive children remain readable inline after the running strip disappears. This is a presentation of the same `subagent.history` available to CLI/TUI and native clients, not new control authority. Current DSH history omits foreground child identity and legacy background job-to-child mapping: those calls remain visible as ordinary launch tools, without guessed links. Pending/failed calls also remain visible; tool return alone never proves the child is done.

The PWA folder chooser offers New folder inside the current directory, then navigates into the created directory; only Use this folder confirms the session working directory. Cancel or a failed creation preserves the previous selection. CLI/TUI use `dirs [path] --mkdir <name>` through the same `workspace.mkdir` request; omitted path means the host home directory. The native local NSOpenPanel also enables New Folder (macOS validation pending).

The two folder pickers are not the same thing. The phone walks the host's own folders through `workspace.list`, which is the only picker that means anything over a remote connection, and `turnwire dirs` gives the terminal the same list. The desktop's panel chooses a folder on the Mac, so it matches the host only when the desktop is talking to a local daemon; a remote desktop connection still needs a typed path.

Deployment uses the same local permission boundary through `/deployment`. Clients submit runtime configuration and display shared asynchronous status; they never run SSH or install services themselves. The daemon owns the job, persists private configuration, strips model credentials from child processes, and connects to the installed Relay through `RemoteController`. Server addresses, login accounts and key paths are required runtime input. Optional advanced settings are available through the shared JSON configuration in every client and native advanced fields. Closing a client leaves the job running; daemon interruption is explicitly reported for recovery.

## Change acceptance

Session management belongs to the session list, not the conversation page: the PWA uses a per-row More menu, and native desktop uses the sidebar row's More/context menu. Rename, archive/restore and existing native export/copy/reveal actions target that row without selecting it or clearing the current conversation draft. Client operation continuations (success, failure and cleanup) are scoped to a connection generation and request owner, and model catalogs are host-scoped. Unversioned action replies cannot replace an entity already advanced by a newer event. History projections retain stable `originSeq` for paging/export identity and optional `displaySeq` for execution order; queued-to-running moves display order once, while subsequent edits retain that position. Native and TypeScript reducers patch user messages consistently instead of treating `message.updated` as a new message type.

Menu expansion is coordinated by the list, with only one row open at a time regardless of pointer or keyboard input. Management results belong to the target session and operation, not the currently selected conversation's runtime-error channel; failures remain visible in the management surface, and late responses cannot close another session's menu. Archived conversations show a read-only notice, not an inline restore action. Sending, stopping, approvals and resuming execution remain conversation interactions; CLI/TUI retain their explicit management commands.

Rename and archive are protocol commands backed by Core metadata and journal events. Archiving retains history, rejects active sessions/pending approvals, and blocks resume/send until restored. Local and encrypted clients see changes through the same event stream. Native Markdown rendering, per-session drafts, result view, content search and approval center are presentation over shared records. The shared projection drops an assistant message that carries no text, so a turn made only of tool calls shows its tool blocks instead of an empty bubble in every client. A prompt sent while a turn is running is queued behind it by default and can instead steer that turn when the client asks for it (`mode: steer`); the recorded message carries `queued` or `steer` while it waits, and the host records the moment a waiting prompt actually starts, so every client can both label it and place it in the turn that ran it. Only `stop` cancels the turn, and it never injects text. A prompt that is still waiting sits above the composer with its own edit, cancel and jump-the-queue controls on that row and nowhere else; the row is the prompt plus those three buttons, so the buttons keep their size, the text is cut to one ellipsised line, and the full text stays on the row for hover or long press. Those controls belong to a prompt that can still be taken back: once the runtime starts it, the row moves into the turn that ran it and cancelling answers that it has already started, rather than erasing a message the model is answering. A long waiting prompt must never widen its box: a box that can be panned sideways is how that failure reads on a phone, and the same holds for the running-agent strip's labels.

The phone/PWA renders assistant event text as CommonMark + GFM (headings, lists, quotes, inline/fenced code, tables, task lists, links and footnotes). Code and wide tables scroll within their own regions; code can be copied. Incomplete streamed fences render as code and update when completed. This renderer belongs to the web presentation layer: it does not change event text, CLI history/export, native rendering or shared session rules. User input and raw tool results retain their literal representation. Raw HTML remains inert and image references appear as explicit links under the existing image policy. The native app already has its own Markdown presentation; the terminal can retain source formatting. The PWA also chooses the session model and reasoning effort, behind a chip in the composer that opens its options against itself rather than in the session heading or as a block above the composer: a phone opens a conversation pinned to the newest message, so a control inside the scrollable region is off-screen exactly where it is needed, a permanently expanded row would cost the composer the height the keyboard needs, and a panel that pushes the input down moves it out from under the finger that is about to type. The panel directly lists runtime models grouped by provider, without a search input or a second confirmation step. Opening focuses the panel rather than a text field, avoiding a search-triggered software keyboard. The current model is checked (`aria-pressed="true"`), including the runtime default before an explicit session selection; button `data-provider` and `data-model` values are the runtime IDs. The dialog is labelled “Model”, and the scrollable list uses `.model-list`. A tap submits the choice immediately; while it is pending, model and effort controls are locked against duplicate submissions. Success closes the panel; failure leaves it open with an inline error and permits retry. A tap outside it or Esc dismisses it, and Esc restores focus to the model chip. The catalog is fetched again when it opens, and again when the host reports a model unavailable, because a route can gain or lose a model while a page sits open: an id that has disappeared from the endpoint must not stay selectable on screen. Models, provider groups and reasoning efforts come only from the runtime catalog, never a client-maintained list. Reopening after success shows the selected model and, when it advertises efforts, the “Reasoning effort” select with the host-resolved value and runtime-advertised options/default. A new model carries the previous one's reasoning effort only when it declares that effort itself; otherwise the host resolves its default, and a model without reasoning efforts has no effort control. Tool calls follow the same rule: a closed row carries the call's own action — the command it runs, the file it touches, the task it delegates — cut with an ellipsis and available in full on hover or long press, so nobody opens a call just to find out what it was. A run of consecutive calls is one line while it is in flight, showing the newest call, and becomes the run's summary ("shell ×3 · All returned") once the last one returns. Opening a run does not draw a box inside a box: the calls indent under a hairline, and the only box is the individual call someone actually opened. A finished turn is shown as its result: once the turn is over, the steps that produced it — the intermediate notes and every tool run — fold into one `Process · N steps` line above the answer, one click away. A turn that is still running stays open step by step, and a turn that failed keeps its steps visible instead of hiding the failure inside the fold.

Start a behavioral feature at its owning shared layer, then expose it through all applicable clients. Check that a command from one client is visible from another without a client-specific restart or database. Use meaningful integration coverage for validation, authorization and lifecycle effects. Swift live tests provide cross-language contract checks. UI-only conveniences can stay native to their platform.

Provider availability must not be confused with host registration. A live Relay connection does not establish that every phone network can resolve and reach its public origin. Cloudflare Quick Tunnel is optional development access; use the deployment guide when selecting a fixed Relay for Mainland China.

The phone always shows a connection state, including on narrow screens: a bar while the link is connecting, unverified or broken — the states that need explaining — and a single thin line once it is verified, carrying the host, the round trip and, on a click, a fresh verification. A failure the link has since answered clears itself when the connection verifies again; a failure that is an answer to what the reader did stays until it is dismissed or superseded. `RemoteClient` publishes health only after an encrypted nonce round trip with the expected Mac. It probes every 15 seconds while the page is open, times out after 5 seconds, and on return to the foreground confirms and reuses the socket it still holds rather than rebuilding it — only a socket that is genuinely gone is rebuilt, so tab switching is not a reconnect. The v2 session waits for host confirmation of the final acknowledgement. The Mac requires an encrypted acknowledgement of its own fresh challenge before marking a device connected; its positive state expires after 25 seconds without another acknowledgement. Relay readiness and saved pairing credentials alone cannot produce a positive connection state. These are recent observations, not a guarantee of future connectivity or background iOS execution.

Explicit event subscriptions from cursor zero can contain thousands of encrypted events. The Relay applies its message ingress rate limit to phones, while authenticated hosts may replay that history without triggering the phone limit. Frame-size and slow-consumer buffer bounds remain enforced for both roles. This is shared transport behavior for every remote client; no client-specific workaround or wire change is required. The regression exercises 4,000 real encrypted events, health confirmation and a following snapshot request, alongside an independent phone flood rejection check.

### On-demand conversation history

`history.page` is a shared read-only Core RPC used by SDK, CLI/TUI, Swift and the phone/PWA. It pages backwards by each record's first event sequence (exclusive `before`), defaults to 40 complete records, and returns `events`, `cursor`, `hasMore`, `nextBefore`. The store maintains a durable projection of messages, tool input/result pairs, approval request/resolution and errors alongside the unchanged raw journal. Store accepts only an empty database or the current final schema; it rejects older, unversioned or malformed databases with `UNSUPPORTED_STORAGE`, without migration or journal backfill. Use a separate empty database rather than modifying the old one. Transport pages are bounded to 512 KiB and oversized text events become explicit 64 KiB previews, marked by `truncation` metadata and visible text. Durable full content stays in the host. `history.record` provides session-scoped, revision-pinned string chunks for explicit full exports; SDK/CLI/TUI and Swift export resolve previews, while interactive readers do not automatically download full bodies. Assembly is capped at 64 MiB per record and fails explicitly if exceeded; a changing record retries at most three times. Swift changes have static/fixture coverage only until a macOS build and live-native run are performed.

Opening a conversation loads the recent page immediately, not thousands of token fragments from the beginning. Web loads the next bounded page when the reader scrolls to the top, without a load button or a session-wide automatic page cap. Initial entry stays on recent messages; failed reads wait for another upward gesture, and stale responses from a previous session are ignored. Swift retains its earlier-records control; CLI/TUI display the next `history --before` command. Search and displayed record counts cover loaded records. Full export is explicit and still visits every page (`export`, native “导出完整会话…”); `history --all` also reads all pages. Loading older pages preserves reading position.

Projected message events carry optional `originSeq` for their original display order and `seq` for their newest incorporated event. Clients reduce live events incrementally, batch visible updates every 50 ms, and cache the projected transcript. Page merges absorb events through the page cursor and replay newer in-flight events exactly once. History must not change live session/approval state: snapshots win over older metadata events. Swift reconnects from a fresh snapshot and recent page. Remote request-only connections use `subscribe {after:"latest"}` for prompt encrypted health verification; an explicit listener then replays from its requested cursor, including the snapshot/listener race window. Explicit subscriptions retain journal order/cursors, but oversized text is previewed; full export uses record chunks. Replay yields between bounded batches and closes overloaded connections instead of accumulating unbounded encrypted writes.

Remote configuration is idempotent for an unchanged active configuration. Tunnel failures retry after 1/2/4 seconds, then stop until explicitly retried; brief successful starts do not reset the budget. Named hostnames retain pairing; temporary addresses may change. Existing `online` state denotes transport readiness, while its message distinguishes local Relay readiness from a fresh device-confirmed path. Runtime snapshots expose optional `busyKnown`: false means unknown, never proof of idleness. The SDK also offers method-linked typed calls and validates successful results against the actual method contract.

Validation: `tests/history.test.ts` covers 4,000 deltas, complete tool pairs, backward cursor boundaries, concurrent updates, local/encrypted parity and snapshot non-regression. CLI/TUI parity tests exercise the same paging command. `scripts/native-live-check.mjs` seeds the same long-history shape for native paging/export/live-update checks. `scripts/history-ui-check.mjs` exercises encrypted browser paging, scroll anchoring, completion and reload at a 390 px viewport. Browser automation is not a physical iPhone/cellular network test.

A Linux installation can run the optional `turnwire-host.service` supervisor (`apps/daemon/src/host-service.ts`) and `bin/turnwire tui`. It launches the same daemon and DSH runtime; TUI remains a client, and SSH/TUI exit does not own host lifecycle. The generated service paths are derived from the installation directory. Each host retains its own private identity, state and remote pairings. No additional remote administration privileges are granted.

### Remote transport v2 and notifications

All TS clients share the SDK's staged connection lifecycle, using retry and session-encryption primitives from `packages/wire`. Native remains Swift/SwiftUI and uses the same local administration and Core RPCs. PWA adds browser-specific notification permission, Service Worker display, and visibility/online hints; its inbox and approval decisions use Core like CLI/TUI/native. Host-wide notification administration remains local-only. Remote users can subscribe/unsubscribe only their own device.

The local native connection does not independently implement browser or Relay lifecycle. Its remote settings expose direct listener configuration, notification availability/preferences, v2 pairing/revocation and device protocol/enrollment status (`pending` or `enrolled`), with no credential-upgrade operation or v1 compatibility. Phone notification delivery is tested with a simulated provider; actual iPhone notification permission, lock-screen delivery and LAN certificate acceptance require device testing.
