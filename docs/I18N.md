# Internationalisation

English is what the product speaks by default; Chinese is the second locale. This page records the
split that keeps the two from drifting apart, and the vocabulary every client shares.

## What is shared, and what is not

- **Shared: the error code.** `packages/protocol` exports `turnwireErrorCodes`, and a client renders
  its own sentence from the code. The daemon's own message stays a concise **English** fallback, so
  `--json` output — and anything a script parses — does not change with the reader's locale.
  Host-side user-visible text is English by rule, and a test enforces it.
- **Per client: the user-visible text.** The PWA, the CLI/TUI and the native app each own a catalog
  with `en` and `zh`. Their media differ (an inline hint, a terminal line, a native alert), so one
  shared sentence would fit none of them well.
- **Enforced: completeness.** Each client has a test asserting that its catalog covers both locales
  and every code in `turnwireErrorCodes`. A missing translation fails CI instead of quietly showing
  English inside a Chinese interface.

When the number of clients grows past a handful, or the string count reaches the thousands, revisit
this: a shared catalog becomes the cheaper option then. Today the shared part is the code (30 of
them) and the per-client part is the prose (roughly 800 entries).

## Locale resolution

| Client | Detection | Override |
| --- | --- | --- |
| PWA | `navigator.language` | a control in the interface, persisted in `localStorage` |
| CLI / TUI | `TURNWIRE_LANG`, then `LC_ALL` / `LANG` | `--lang en` or `--lang zh` |
| Native app | `Locale.current` | General settings, persisted in `UserDefaults` |

`--json` output is never localised.
